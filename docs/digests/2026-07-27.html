Code Review Breaks, Chatbots Fade

AI-generated code is burying engineers in review debt, Ethan Mollick declares the chatbot era is ending, and the industry is quietly discovering that routing models intelligently is harder than it looks. Three distinct inflection points converging on the same week.

The Code Review Crisis Nobody Planned For

Engineering leaders have a new problem that wasn't in any AI adoption playbook: AI coding tools are generating code faster than humans can review it, and review quality is visibly degrading. The Pragmatic Engineer's latest Pulse, published July 23rd, identifies this as an emerging trend at the top of mind for eng leaders — "massive increase in code review load" is the new complaint, and it's not abstract. Reviewers are starting to rubber-stamp PRs they'd normally catch, because the volume is simply too high.

This is the second-order effect of shipping AI coding tools without rethinking the development workflow. The productivity gain accrues to the author; the cost lands on the reviewer. A single engineer using Claude Code or Copilot can now generate 3-5x the diff volume they used to. But a PR reviewer still reads line by line. The math doesn't work.

There are no proven solutions yet. Some teams are experimenting with AI-assisted review, which risks a hall-of-mirrors failure mode where AI reviews AI-generated code with neither party catching the subtle semantic error. Others are raising PR size limits or requiring more granular commits. Neither addresses the root issue: trust and verification in an AI-assisted codebase require new norms, not just new tools.

"Many questions, but few proven solutions."

— Ivan Klaric, The Pragmatic Engineer

The shops most at risk are mid-size teams that adopted AI coding tools aggressively but kept their review process unchanged. The ones ahead of this are starting to treat review throughput as a first-class eng metric alongside PR velocity — and realizing they're diverging fast.

Mollick Calls Time on the Chatbot Era

Ethan Mollick's June 30th essay "The Twilight of the Chatbots" is getting renewed traction this week, and it deserves more attention than it received at publication. His argument is structural, not polemical: the chat interface — type a message, get a response, repeat — was never the destination. It was a scaffold while the real capabilities were being built. Now that agents can hold context, take multi-step actions, and operate asynchronously, the one-turn chat loop looks increasingly like training wheels.

Mollick frames this as how work changes "along the exponential" — meaning the same underlying capability improvement that makes GPT-5-class models impressive in conversation makes them genuinely transformative when embedded in workflows that don't look like chat at all. The chat interface stuck around because it was the easiest thing to ship, not because it was the best fit for the capability.

The read-across for product teams is uncomfortable. A lot of current AI product surface area — the chat tab, the sidebar assistant, the floating input box — is optimized for a paradigm that's already aging. Products that are architecting around agent loops, tool use, and background task execution are positioning for where the interface gravity is actually heading. The chat interface isn't going away, but it's becoming the fallback, not the primary surface.

"We often lack the tools for the job, even if the AI is capable enough."

— Ethan Mollick, "Claude Dispatch and the Power of Interfaces" (March 2026)

Mollick isn't predicting a specific date or product that displaces chat. He's pointing at a direction. The teams that clock this early get to design the next default interface; the ones that don't will spend 2027 rebuilding what they just shipped.

Model Routing: Simple in the Pitch Deck, Brutal in Production

Two pieces landed in the same week making the same point from different angles: intelligent model routing is one of those ideas that sounds clean in a slide and falls apart under real conditions. IBM Research's post on Hugging Face from July 15th walks through why routing — sending cheap queries to a small model, expensive ones to a frontier model — creates cascading complexity the moment you have to define what "hard" means without labeled data. And Gergely Orosz's July 2nd Pulse surveyed the actual tooling landscape for smart routing and found it thin: a handful of solutions exist, but most require significant calibration work before they pay off.

The failure modes are specific. Routing based on prompt length misfires constantly — a short question can require deep reasoning; a long prompt can be trivially answered by a small model. Routing based on task type requires classification that is itself a model inference call, adding latency. Routing based on confidence scores from the small model is circular: if the small model knew it couldn't answer well, it wouldn't need a bigger model to bail it out.

"Are there any 'intelligent' router solutions out there which select the right model for the right task? I looked into it, and there are a few options."

— Gergely Orosz, The Pragmatic Engineer

The teams actually making routing work are doing it with domain-specific heuristics — routing by request category pre-classified at intake, not by dynamic inference. It's less elegant than a universal router but it ships. The lesson from both pieces: treat routing as a product feature with its own eval loop, not an infrastructure optimization you bolt on after the fact. The latency and cost wins are real, but only if your routing logic is tested as rigorously as the models themselves.

LLMs as Security Tooling: Eugene Yan's Threat Model Framework

Eugene Yan's May 27th piece "Using LLMs to Secure Source Code" has been circulating steadily through security-adjacent engineering channels, and its practical framework holds up better than most of what gets written in this space. The workflow Yan lays out is five-stage: build a threat model, discover vulnerabilities, verify, triage, then patch — and LLMs slot into each stage differently, with different reliability profiles.

The most useful distinction in the piece is between discovery (where LLMs genuinely excel, especially at surfacing insecure patterns, injection points, and authentication gaps across large codebases quickly) and verification (where they're unreliable, tending toward false confidence on whether a theoretical vulnerability is actually exploitable). Yan's prescription: use LLMs aggressively for the breadth pass, then apply human judgment for the depth pass on high-severity findings.

This is a meaningful capability for AI product teams specifically. If you're shipping with Claude Code or Copilot generating significant portions of your codebase, you have a higher baseline of AI-generated code that hasn't been through the same mental security review a human author applies while writing. Running an LLM-driven threat model pass before major releases — not as a substitute for a real security review, but as a first-pass triage layer — is now cheap enough to be worth institutionalizing.

"Build a threat model, discover vulnerabilities, verify, triage, and patch."

— Eugene Yan, "Using LLMs to Secure Source Code"

The piece doesn't oversell. Yan is explicit that LLMs will miss things and hallucinate others. But as a force multiplier on a security engineer's time — or as a first-pass tool for teams without dedicated security staff — the workflow is practical and replicable today.

Local Coding Agents: The Subscription Fatigue Alternative

Sebastian Raschka's June 27th piece "Using Local Coding Agents" arrives at an interesting moment — right as the code review debt story above is making people question whether the productivity gains from cloud AI coding tools are actually showing up in shipped quality. Raschka's angle: open-weight models running locally in coding harnesses like Continue.dev or Open Interpreter are now credible alternatives to Claude Code and Codex subscriptions for a meaningful subset of tasks.

The honest framing is that "credible alternative" does a lot of work. For greenfield feature work on well-understood domains, local models like Qwen2.5-Coder-32B or DeepSeek-Coder-V2 perform respectably at zero marginal cost per token. For complex refactors, multi-file reasoning, or anything requiring deep context over a large codebase, the frontier models still win clearly. The question is whether your actual daily task distribution is concentrated in the first category.

The subscription fatigue angle is real. Orosz documented in June that engineering departments are actively looking to cut AI spend — not because the tools don't work, but because $20-40/month per engineer across a 200-person org adds up to $50-100K/year before you get to API costs for product features. Local agents running on developer hardware have zero marginal cost and no data egress concerns, which clears two objections simultaneously.

"Using Open-Weight Models in Local Coding Harnesses as an Alternative to Claude Code and Codex Subscriptions."

— Sebastian Raschka, Ahead of AI

The practical move for teams feeling cost pressure: benchmark your most common task types against a local model before defaulting to the assumption that frontier is always necessary. For many teams, a hybrid — local for drafting, frontier for review and complex reasoning — may thread the needle.

What This All Means

  1. The code review debt problem is real and it's yours to solve now, not later. If your team has meaningfully increased AI-assisted code output without rethinking review throughput — who reviews what, at what depth, with what tooling — you're already accumulating risk. Audit your PR merge velocity against your actual review time per line before the next quarterly planning cycle.
  2. Chatbot-first product architecture has a shelf life. Mollick's "twilight" framing isn't hyperbole — it's a timing call. If your core user interaction is still a chat input box in 2026, you should have a concrete answer for what the post-chat surface looks like for your product, even if you're not building it yet.
  3. Model routing requires its own eval discipline. The IBM Research and Pragmatic Engineer pieces together confirm that shipping routing without a dedicated test suite is shipping a bug. Treat your routing logic as a first-class feature: define what correct routing looks like, build labeled test cases, and measure it the same way you'd measure model output quality.
  4. LLM-assisted security review is cheap enough to be standard practice. If your team is generating significant AI-assisted code and not running a structured LLM threat modeling pass before major releases, you're leaving an inexpensive risk mitigation on the table. Yan's five-stage framework is a workable starting template — start with the discovery pass and triage by severity before investing in the verification layer.
