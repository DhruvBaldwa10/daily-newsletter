GPT-5.6, Memory Stacks, ARC-AGI Tricks

OpenAI shipped GPT-5.6 yesterday with a technical trick that tripled its ARC-AGI-3 score overnight. Meanwhile, researchers are rethinking how agents remember things at a foundational level, and a new benchmark puts economic cost at the center of agent evaluation.

GPT-5.6 and the ARC-AGI-3 Score That Shouldn't Have Tripled

OpenAI dropped two posts on July 29th that deserve to be read together. The first announced GPT-5.6 — positioned as a frontier-efficiency fusion, delivering more intelligence per dollar across inference and agentic workflows. The second was the more technically striking one: enabling two API settings tripled GPT-5.6's score on ARC-AGI-3.

The two settings in question are reasoning retention (carrying the model's chain-of-thought across turns rather than discarding it) and compaction (summarizing older reasoning to prevent context bloat). Neither is a new model capability — they're serving-layer configuration choices. That a 3x benchmark gain falls out of two toggles says something uncomfortable about how much performance is being left on the table in default API configurations, and how much benchmark competition is really a game of serving-stack tuning rather than pure model capability.

The efficiency framing from OpenAI is deliberate. "More useful intelligence per dollar" lands differently in a market where Anthropic just launched Opus 5 at half the price of its predecessor, and where poolside's Laguna S 2.1 has been undercutting DeepSeek on cost. The race isn't just about who has the smartest model anymore — it's about who can make the smart model cheap enough to run in loops.

"GPT-5.6 improves AI efficiency across models, inference, and agentic workflows, helping deliver more useful intelligence per dollar."

— OpenAI Blog

For teams building agentic pipelines on the OpenAI API, the compaction and reasoning-retention settings are worth testing immediately — especially if you're running multi-turn tasks where context accumulates fast.

Agent Memory Is Getting a First-Principles Redesign

Three separate research threads published this week converge on the same diagnosis: agent memory is the weakest link in the stack, and bolting retrieval onto the context window isn't going to fix it.

The most ambitious proposal is Metis, which argues that memory shouldn't be an external module at all — it should be a native capability baked into foundation models. The paper introduces what it calls "memory foundation models," trained to internalize persistent context the way multimodal models internalized vision. That's a long-horizon research bet, not a shipping artifact, but the framing is significant: if memory becomes a model-native primitive, the entire ecosystem of external memory services (Mem0, MemGPT, Zep) gets disrupted from below.

More immediately applicable is the Neo4j-backed bitemporal memory store from Niksarli and Baheti. Their system keeps memory agent-local in a property graph augmented with HNSW vector indexes, with a full bitemporal data model so you can query what the agent "knew" at any point in time. That last part matters for debugging: when an agent makes a wrong decision, you can replay its memory state at the moment of failure rather than guessing.

Then there's InferScale, which attacks the problem from the serving side. When memory systems like Mem0 retrieve a context slice and inject it into the prompt, the serving engine re-prefills that content on every request — even if it's identical to the last one. InferScale proposes GPU-native KV injection to skip that redundant computation, directly cutting time-to-first-token as memory budgets grow.

"Production memory systems retrieve a relevant subset of this memory and inject it into the prompt, forcing the serving engine to repeatedly prefill the same content. As the retrieval budget grows, time-to-first-token increases even though the underlying memory is unchanged."

— InferScale paper abstract, arXiv 2607.27090

These three papers aren't coordinated, but together they sketch a roadmap: near-term, smarter KV management; mid-term, graph-native memory with temporal queries; long-term, memory that lives inside the weights.

MCP Connectors Won't Replace a Real Context Engine

The question on Hacker News this week — "If Claude/Codex can connect via MCP, what do we need a context layer for?" — is exactly the kind of thing that sounds smart in a Slack thread and falls apart under pressure. The Unblocked team's answer is worth reading carefully.

Their argument: MCP connectors solve the retrieval routing problem (which tool to call, and how to authenticate) but don't solve the context quality problem (what to include, in what form, at what level of granularity, and how to keep it fresh). An MCP server that returns raw GitHub issues or Notion pages dumps the decision of "what's relevant" back onto the model, which has no persistent understanding of the codebase's history, the team's conventions, or what the user is actually trying to accomplish. A context engine makes those decisions explicitly — it's an abstraction layer that the model shouldn't have to reconstruct from raw tool outputs on every turn.

Simon Willison's TIL on connecting custom MCP servers to Claude and ChatGPT is a nice complement here: he found it works, but takes "quite a few steps." That friction is real today. As MCP tooling matures, the workflow will get smoother — but Unblocked's point stands that retrieval access isn't the same as retrieval intelligence.

"Connecting a custom MCP server to Claude and ChatGPT's standard chat interfaces is possible, but can take quite a few steps."

— Simon Willison

The practical implication for teams designing data pipelines for agents: MCP is a transport layer. You still need someone deciding what gets transported, when, and why — whether that's a purpose-built context engine or a very carefully designed set of MCP server instructions.

Can Agents Do Real AI Research? A New Study Tries to Find Out

AI labs have been forecasting that AI agents will soon automate AI research itself — the so-called recursive improvement loop that underpins most aggressive capability timelines. A new paper from Kirgis, Kapoor, Schwartz, and Rabanser takes a harder look at whether agents can actually conduct open-ended AI research, and the methodology is more interesting than the headline.

The problem with existing evaluations, they argue, is that they either test on narrow verifiable tasks (which excludes anything that looks like real research) or submit AI-generated papers to peer review (which is too noisy and slow to be a reliable signal). Their "third way": put an agent on a central, open-ended research problem — not a toy — and assess progress against a rubric that captures what a researcher would actually do: forming hypotheses, designing experiments, interpreting unexpected results, updating priors.

The paper is framed as "early evidence from two case studies" rather than a sweeping claim, which is the right epistemic posture. The finding — that current agents can make partial progress on open-ended research tasks but reliably fail at the judgment calls that define mature research — lands differently when you've watched Claude or GPT-5.6 run for hours on a complex codebase and produce something that looks right until it doesn't.

"Current evaluations either test agents on narrow, verifiable tasks, which excludes open-ended research, or submit AI-generated papers to blind peer review, which is overstretched, stochastic, and suffers from poor review quality."

— Kirgis et al., arXiv 2607.27191

This connects to a parallel paper: OmegaUse-OfficeVal, a 100-task benchmark for LLM agents on office-suite workflows, notable for adding "economic grounding" — each task has an associated cost ceiling, forcing the evaluation to ask not just "did the agent complete it" but "did the agent complete it at a price that makes sense." That framing should become standard in every agent benchmark.

Parallel Claude Code Agents Need Traffic Management

The gap between "run multiple Claude Code agents in parallel" and "run multiple Claude Code agents in parallel without them clobbering each other's work" is where a lot of teams are currently stuck. A new open-source project, claude-code-merge-queue, addresses this with a local merge queue specifically designed for parallel agent workflows — essentially a serialization layer that lets agents work concurrently but commit sequentially, with conflict detection before merge.

The project is early (18 HN upvotes, 6 comments), but the problem it's solving is sharp. When you run three Claude Code instances on separate features and they each touch shared utilities or config files, the last write wins — which is fine for humans with git blame and pull request review, but breaks down in autonomous agent loops where there's no human in the merge path. The merge queue enforces an ordering discipline that makes parallel agent work safe to run unattended.

A related project showed up the same day: peri, a Rust coding agent built to be compatible with Claude Code plugins and skills. The Claude Code ecosystem is starting to develop the kind of third-party tooling that signals a platform is maturing — agents that compose with other agents, orchestration primitives that manage conflict, alternative runtimes that share the same plugin surface.

"A local merge queue for parallel Claude Code agents."

— funador, GitHub / Hacker News Show HN

Sebastian Raschka's recent deep-dive on controlling reasoning effort in LLMs is relevant context here: if you're running parallel agents, you probably want them in low-effort mode for most subtasks and high-effort mode only at decision points. Knowing how models learn to shift between those modes gives you better levers for cost management at scale.

What This All Means

  1. Two API configuration toggles — reasoning retention and compaction — tripled GPT-5.6's ARC-AGI-3 score without any model change. Before attributing benchmark gaps to model capability, audit your serving configuration; you may be leaving significant performance on the table through defaults.
  2. Agent memory is fracturing into three separate engineering concerns that are easy to conflate: retrieval routing (MCP solves this), context quality and freshness (requires explicit design, not just tool access), and serving-layer efficiency (InferScale's KV injection attack). Treat them as separate layers in your architecture, not one "memory" bucket.
  3. OmegaUse-OfficeVal's move to cost-grounded benchmarking — evaluating agents against a price ceiling, not just task completion — is the right framing for production. Start defining cost budgets per task class in your own evals now, before the compute bill makes it urgent.
  4. The Claude Code third-party ecosystem (merge queues, Rust runtimes, plugin-compatible agents) is moving fast enough that it's worth checking GitHub weekly. The parallel-agent coordination primitives being built today are what multi-agent pipelines will standardize on in six months.
